# v1.4.0 plan — core extraction

**Status:** AGREED 2026-10-17 (decisions recorded at the end). In progress: Phase 0 done 2026-10-18 (baseline a80994a); Phase 1 done 2026-10-24 (step 1 on 2026-10-23, steps 2-6 on 2026-10-24).

## Goal

Make the emulation core independent of WinForms, so that MZRakuCLI
(v1.6.0) and the cross-platform GUI (v2.0.0) are new front ends on
an unchanged core rather than surgery across the codebase. See
`roadmap.md`.

**Tag-only release**, like v1.2.0: no packaged download and no
README change (the README keeps describing v1.3.0). The next
packaged release is v1.5.0, built on this core.

### Ground rules

- **No behaviour change.** Every machine must look, sound and respond
  exactly as in v1.3.0. The regression suite is the referee.
- **Regression coverage before refactoring.** Golden images and
  traces are approved on the unmodified v1.3.0 code (Phase 0) before
  any Phase 1 commit.
- **Bugs found along the way are recorded, not fixed**, unless the
  fix is needed for the refactor itself. They go to v1.5.0 or the
  backlog, so this release stays a pure refactor.
- **Small commits, suite after each.** Run the regression suite
  before every commit from Phase 1 on.

## Where things stand (survey, 2026-10-17)

| Area | Lines | WinForms-free? |
|---|---|---|
| `Hardware/` (chips, video, keyboard, sound, cassette) | ~10,200 | Mostly |
| Machine classes, `Settings`, `AutoLoadOrchestrator`, `DumpTraceRecorder` | ~5,000 | Mostly |
| `MainForm.cs` (1,800) + `UI/` | ~10,600 | No (front end) |
| Z80Core (submodule) | ~2,000 | Yes |

`MZRaku.csproj` has `ImplicitUsings` with `UseWindowsForms`, so
`System.Drawing` and `System.Windows.Forms` are in scope in every
file. Explicit `using` lines therefore under-report the
dependencies. The type-level survey found:

| Dependency | Where | Notes |
|---|---|---|
| **`Keys`** (WinForms key codes + modifier flags), ~160 references | `KeyboardMatrixBase`, `Keyboard`, `Mz80aKeyboard`, `Mz800Keyboard`, `SpecialKeyMap` + `Mz80a`/`Mz800` variants, `KeyOverride`, `KeyboardDiagnostics`, the three `*KeyboardLayout` classes | **Persisted by name**: `[KeyOverrides.*]` in `settings.ini` and `.mzkbd` files store `Keys` names (e.g. `F5`, `Control, G`) and parse them with `Enum.TryParse<Keys>`. |
| **`Bitmap`** / `LockBits` / `PixelFormat` | `Video`, `Mz80aVideo`, `Mz800Video` (`Frame`, `FrameHi`, `GetGlyph`), `IMachine.VideoFrame`, the three machine classes, `DumpTraceRecorder` (`Bitmap.Save` PNGs) | The Font Sheet and keyboard editor use `GetGlyph`. |
| **winmm P/Invoke** | `WinmmWaveOut` (6 imports), `JoystickInput` (2) | `Sound` owns a `WinmmWaveOut` and a real-time feed thread. `JoystickInput` is created and polled by `MainForm`. |
| **`MessageBox`** | `MatrixValidation` (startup drift warning); `AutoLoadOrchestrator` already takes an `Action<string>` | `Program.cs` uses it too, but that stays in the front end. |
| user32 P/Invoke | `MainForm` only | Front end; stays. |

Other findings that shape the plan:

- **Keyboard input has two halves.** `MainForm` passes key-down/up
  events (`Keys` code plus modifier flags) **and**, separately, the
  layout-translated character from `KeyPress`. The core keyboards
  combine the two, for example for the UK `'` / `@` shift handling.
  Per-machine routing differs: the MZ-80A has no shift argument, and
  `ProcessCmdKey` handles Tab, Pause, Scroll Lock and Alt+Enter
  first. SDL has the same two halves (scancode events and
  `SDL_TEXTINPUT`), so the contract carries over.
- **MZ-700 and MZ-80A sound is generated in real time** on `Sound`'s
  feed thread, which samples the PIT gate/reload state as it runs.
  It isn't deterministic, so it can't be compared like a golden
  image. Only the MZ-800 records deterministic audio
  (`AudioCapture`, written as `<dump>.wav`).
- **The regression suite depends on the developer's own
  `settings.ini`.** It runs `bin/Debug/.../MZRaku.exe`, which reads
  the settings and ROMs next to it. A local change, such as
  `DefaultMachine`, display options, the MZ-1R25 or key overrides,
  can change results.
- **The suite is MZ-800-only in practice** (16 MZ-800 cases, plus
  one BASIC boot each for the MZ-700 and MZ-80A). It lives in the
  frozen `_machineinfo/_mz800info/_regression/`.
- **`fist` flaked once** (2026-10-17: 4,394 px on a build+run, then
  passed 3/3 solo and 18/18 on a rerun). The cause is unknown.
- **`MainForm` hosts the machines**, not just the UI. It creates the
  machines, loads ROMs, starts them, steps frames, loads cassettes,
  BASIC and BASIC source, switches machine, routes input, runs the
  autoload orchestrator and drives `--dump`.

## Design decisions

All decisions confirmed 2026-10-17 (see "Decisions" at the end).

**D1 — Host key codes: `HostKey` mirrors WinForms `Keys` exactly.**
A core `[Flags] enum HostKey` with the same member names and
numeric values as `System.Windows.Forms.Keys`: Windows virtual-key
codes plus the `Shift`/`Control`/`Alt` modifier flags and the
`KeyCode`/`Modifiers` masks. As a result:
- the `settings.ini` and `.mzkbd` formats are unchanged, including
  `ToString()` forms like `Control, G`;
- the WinForms front end converts with a cast;
- MZRakuCLI maps SDL scancodes onto these values.

It follows the canonical-reference pattern: a startup check (in the
WinForms front end) asserts that every `Keys` member has a
`HostKey` twin with the same value and `ToString()`. A round-trip
check reads and re-saves an existing `settings.ini` and `.mzkbd` and
expects identical bytes.

**D2 — Input contract: key events plus text events.**
The core accepts three events:
- `KeyDown(HostKey keyData)`;
- `KeyUp(HostKey keyData)`;
- `Text(char c)`.

These mirror today's `KeyDown` / `KeyPress` / `KeyUp` exactly. A
single per-machine entry point, for example on `IMachine` or an
`IKeyboardInput`, replaces the three-way branching in `MainForm`.
Shift derivation (`e.Shift || IsShiftKey`) moves into the core with
unchanged logic. `ProcessCmdKey`'s front-end hotkeys stay in the
front end.

**D3 — Frames: a plain pixel buffer.**
A core `FrameBuffer` holds width, height and an `int[]` of ARGB
pixels, the same 32bpp ARGB layout as today's `Bitmap`s.
`VideoFrame`, `Frame`/`FrameHi` and `GetGlyph` return it. The
WinForms front end copies it into its `Bitmap`s at the edge, with
one shared helper. `DumpTraceRecorder` writes PNGs with a small
built-in encoder (`ZLibStream`); the harness compares decoded
pixels, so encoder differences don't matter.

**D4 — Audio: an output interface; the real-time path unchanged.**
`IAudioOut` covers adding samples, buffered duration, reset and
dispose. `WinmmWaveOut` implements it, and `Sound` receives one from
the front end. The feed thread and its timing logic are unchanged.

**D5 — Joystick: a source interface.**
`IJoystickSource` provides poll, current state and button indices.
`JoystickInput` (winmm) implements it.

**D6 — No dialogs in the core.**
`MatrixValidation` raises its warning through a callback or event
instead of `MessageBox`. The front end shows it as today.

**D7 — Project split: `MZRaku.Core` in `Core/` (confirmed).**
A `net8.0` class library (no `-windows`), referenced by the
WinForms app. The compiler then *proves* the boundary: a stray
`Keys` or `Bitmap` won't build. Recommended layout: move the core
files into `Core/` with `git mv` (history follows renames). The app
project excludes `Core/**` the way it already excludes `tools/**`
and `Z80Core/**`, because the main csproj globs every `.cs` file.
The alternative, leaving files in place and splitting by glob, is
less churn but a confusing tree.

`Core/` stays in this repo: one history, no submodule, and core and
front-end changes land together. It can be split into its own repo
later, as Z80Core was, if a consumer outside this repo appears.
`git filter-repo` can follow the files through the `git mv` rename,
keeping their pre-move history; a plain `git subtree split` would
not. Keeping the split cheap costs nothing now:
- Core depends only on Z80Core, through a relative project
  reference;
- Core never references the app;
- namespaces stay as they are.

A libretro core (RetroArch) is a distant possibility. It would more
likely be a port of the core than a consumer of the .NET library,
but a self-contained core with clear seams (input, frames, audio,
session) is the right starting point for either.

**D8 — Extract machine hosting from `MainForm` (confirmed for v1.4.0).**
An `EmulatorSession` in the core owns:
- creating the machines from settings, and ROM resolution;
- start and reset (switching machine means a new session; see Phase 2);
- frame stepping;
- cassette, BASIC and BASIC-source loading;
- the autoload orchestrator;
- input routing (D2);
- the dump/trace recorder.

`MainForm` becomes view, menus, dialogs and pacing. MZRakuCLI needs
exactly this, so doing it now avoids duplicating `MainForm` logic
later. It is also the riskiest phase (state and ordering inside a
1,800-line form). Kept in v1.4.0 because it is foundational for
both later front ends.

**D9 — Regression suite: tracked harness, isolated, local goldens.**
- The harness script moves to `tools/regress/regress.py`
  (tracked; it contains nothing copyrighted).
- Golden images, outputs and the run sandbox live in a git-ignored
  `_regression/`.
- ROMs, BASIC and test software come from
  `_mz-information-repository/`.
- Each run uses a **sandbox**: a copy of the build output, plus
  fixed per-suite `settings.ini` files and the ROMs. Results no
  longer depend on your own settings, and your settings are never
  touched.

**D10 — Headless runner (confirmed for v1.4.0).**
After the split, a small console front end
(`tools/MZRakuHeadless`) runs a session unpaced and writes the same
dump files. Two benefits:
- **Proof.** Its output must match the WinForms goldens bit for bit,
  which is the strongest evidence the core really is front-end
  independent.
- **Speed.** It is likely much faster than real-time pacing.

It is the skeleton of MZRakuCLI. It depends on D8.

*Done 2026-10-18.* Run with `python tools/regress/regress.py`.
- Each case gets a fresh `_regression/sandbox/<case>/`: the build's
  binaries, `tools/regress/settings.ini` (tracked, shipped defaults)
  and the ROMs.
- The harness pins each ROM's SHA-1 and refuses to run on a mismatch.
- `egg.zip` is rebuilt from the repository's two extracted `.mzf`
  files; the emulator reads zip entries in name order, so the result
  is the same tape.
- The goldens were copied, not moved, so the frozen harness still
  runs.
- All 18 existing cases matched their goldens in the sandbox at
  11cb6d1, so no settings difference needed explaining.

**0.2 Scripted host input: `--keys=<file>`.**
A frame-stamped script, injected at `MainForm`'s key handlers, so
it exercises the real path including per-machine routing and
`ProcessCmdKey`. Example:

```
# frame  action
300  type "PRINT 1+2"     ; per char: KeyDown(VK+mods), Text(char), KeyUp
310  key  Return
400  down LShiftKey
405  key  F1
410  up   LShiftKey
```

- `type` maps characters to key code and Shift through a fixed
  reference layout (UK), and sends the character itself as the text
  event. The script is therefore independent of the host's keyboard
  layout.
- Key names are `Keys` names (D1).
- Unknown names or out-of-order frames fail loudly with a non-zero
  exit code.
- The same script format becomes MZRakuCLI's automation input
  later.

*Done 2026-10-18.* `KeyScript.cs` parses the script; `MainForm`
injects the events after each frame through `ProcessCmdKey`,
`OnKeyDown`, `OnKeyPress` and `OnKeyUp`. The harness resolves
`--keys=<file>` against `tools/regress/keys/`.
- **Timing:** `type` and `key` hold each key for 4 frames, then
  leave a 4-frame gap. A command can't start before the previous
  one finishes.
- **Modifiers:** `type` wraps shifted characters in real `ShiftKey`
  down/up events. Left/right modifiers are reported as the generic
  key, as Windows does.
- **Text events:** `key` and `down` send text only for Return, Back,
  Tab, Escape and Space. Any other printable key must use `type`.
- **Frame clock:** frames count from launch. A scripted reset
  restarts `--dumpframe`'s count but not the script's.
- **Errors:** a bad script exits with code 2, with a line-numbered
  message on stderr (plus a dialog outside `--dump` runs).
- **Verified:**
  - "PRINT 1+2" plus Return prints 3 on all three machines.
  - On the MZ-80A, PC-shifted capitals arrive as lowercase, the
    authentic inverted shift, which shows the real host-key path is
    used.
  - A scripted Ctrl+R reaches System → Reset.
  - The typed runs were byte-identical over three runs.
  - All 18 existing cases still match.
- **Still to come:** the typing regression cases themselves arrive
  with 0.4.

**0.3 Deterministic sound capture for the MZ-700 and MZ-80A.**
- When dumping, the core logs every sound-relevant register change
  (emulated cycle, PIT channel 0 reload, gate, mask and the MZ-80A
  equivalents) to `<dump>.snd.txt`. The harness compares the log
  exactly.
- The real-time feed thread is untouched.
- The MZ-800 keeps its `.wav` comparison.
- Listening checks stay in the release check.

*Done 2026-10-18.* The log is taken at `Sound`'s inputs rather than
at the PIT and PPI registers. The feed thread reads only four
values, so recording every change to them is exactly what reaches
the speaker:
- the soft gate (MZ-700 PPI PC3);
- the hard gate ($E008 D0, and reset);
- the counter reload the machine hands over at frame end;
- the input clock (the MZ-80A switches between C0 and C1).

Format and wiring:
- One `<cycle> <input>=<value>` line per change, after an `init`
  line holding the starting state.
- Repeated writes of the same value are skipped, because the feed
  loop can't hear them (the pulse-hold only counts down while the
  gate is closed).
- `MainForm` starts the log only for `--dump` runs on the MZ-700
  and MZ-80A, and `DumpTraceRecorder` writes it.
- The harness compares it line by line (artefact `snd`). The
  `mz700_basic` and `mz80a_basic` cases now include it, with goldens
  approved.

Verified:
- Logs were identical over three runs, and 18/18 cases match.
- A typed `MUSIC "CDE"` logs the expected notes. The MZ-700 shows
  reloads 4236, 3774 and 3362; the MZ-80A shows 3822, 3406 and 3034
  (261.6, 293.7 and 329.6 Hz from its 1 MHz C0).
- Observation, not fixed (pure refactor): the MZ-700 boot tone's
  hard-gate pulse lasts 138 cycles and comes before C0's reload is
  handed over at frame end. Whether it sounds depends on the feed
  thread's timing and the pulse-hold. This is the parked "MZ-700
  sound loose ends" item.

**0.4 New cases.** Candidates come from `_mz-information-repository`.
The music programs are small BASIC `.mzf` files built with
`tools/MzfBuilder` and kept with the suite's local inputs.

| MZ-700 (6) | MZ-80A (6) | MZ-800 (15) |
|---|---|---|

If `fist` can't be made stable in 0.5, `highway` replaces it. |

That makes 27 cases. The existing suite takes about a minute with

*Done 2026-10-18.* 27 cases; a full run takes about 2 minutes 10
seconds. Every MZ-700 and MZ-80A case also compares `.snd.txt`.
- **MUSIC programs are typed through `--keys`**, not built as
  `.mzf` files. The input is then a tracked script in
  `tools/regress/keys/` rather than another local file.
  `TEMPO 6:MUSIC "C3E3G3+C5R1-A2#F2B5"` covers octaves, a sharp,
  durations and a rest. The MZ-80A types it in lowercase.
- **Machine-code games:** a scripted Space takes Space Panic and

  attract screens into play. This tests that each game reads the
  keyboard and fills its sound log (27 and 620 events).
- **Typing cases:** the same script shape on all three machines:
  - a line with letters and digits;
  - a line with 25 shifted symbols;
  - a cursor edit (Up ×2, Right ×10, overtype);
  - a stored `30 PRINT "…"` holding characters typed in
    GRAPH/GRPH mode;
  - LIST and RUN. The MZ-800 uses F2's default `LIST ` definition.
- **Script timing:** scripts leave about 30 frames after each
  Return. The MZ-80A has no type-ahead, so a key pressed while
  BASIC is still answering is lost: the first try gave `IST` and

- **Other new cases:** monitor boots; Dragon Caves (title screen);
  and COLDITZ, a BASIC tape on the MZ-80A, which takes the typed

- **Goldens** for the new cases were approved provisionally after a

**0.5 Determinism.**
- Run the full suite five times. Every case must match every run.
- Investigate the `fist` flake. Candidates: wall-clock-dependent
  autoload timing, or joystick polling being skipped only once the
  trace exists.
- A case that can't be made stable is fixed, or excluded with a
  recorded reason, before Phase 1.

*Done 2026-10-18.* Five full runs of the 27 cases (135 case runs)
all matched, `fist` included.

The flake's cause can't be proven after the fact. The emulation reads
no wall clock, and saved debugger breakpoints are armed only when the
Debugger window opens. The joystick was already skipped in dump
runs. One outside input was left: **the real keyboard**.
- Every dump run opened a window and **grabbed focus**, with an
  injected system-wide Alt press plus `SetForegroundWindow` and
  `Activate`.
- So keys typed elsewhere during a suite run, or one run's injected
  Alt, could reach a game window mid-run. `fist` reads the keyboard,
  and a 4,394 px difference fits a stray keypress.

Closed in three places:
- **`MainForm`:** `--dump` runs ignore the real keyboard
  (`IgnoreHostKeys` in `ProcessCmdKey`, `OnKeyDown`, `OnKeyPress`
  and `OnKeyUp`), as they already ignore the gamepad. Scripted
  `--keys` input still gets through.
- **`MainForm`:** `--dump` runs skip the start-up focus grab in
  `Shown` and `OnShown`.
- **Harness:** each run starts minimised without activation
  (`SW_SHOWMINNOACTIVE`). A suite run now neither covers the screen
  nor takes focus; checked with `GetForegroundWindow`.

The five runs were repeated on the build with these changes: 27/27
every run.

**0.6 Approve.** Approve all goldens on unmodified `main`, and
record the commit SHA in `_regression/README.md`. From here, every
commit runs the suite.

*Done 2026-10-18.* All 27 goldens were approved on `a80994a`, a
clean `main`. A verification run gave 27/27.

### Phase 1 — Leaf decoupling (still one project)

Each step is one or a few commits, suite after each.

1. **Frames (D3).**
   - `FrameBuffer`, the three video classes, `IMachine.VideoFrame`
     and `GetGlyph`.
   - WinForms edge helper: Font Sheet, keyboard editor, main view.
   - PNG encoder in `DumpTraceRecorder`.
   - Measure frame cost before and after (one 640×200 copy per
     frame at most).

   *Done 2026-10-23.* `FrameBuffer` (`Hardware/`) holds `int[]`
   ARGB pixels with no row padding. The renderers write into it
   through `fixed` pointers instead of `LockBits`, and the glyph
   caches hold frame buffers. `FrameBufferBitmap` (`UI/`) is the
   WinForms edge: the main view keeps one `Bitmap` and copies into
   it per paint, and the Font Sheet converts each cached glyph as it
   draws. `PngWriter` writes RGBA PNGs with `ZLibStream`, so dumps no
   longer use GDI+. Release-build timing per frame, render plus the
   new copy (before → after): MZ-700 text 212 → 213 µs, MZ-800
   320-mode 121 → 130 µs, MZ-800 640-mode 160 → 218 µs, against a
   16.7–20 ms frame. Suite 27/27. The paint path and the Font Sheet
   aren't visible to the suite, so they were checked on screen on all
   three machines.
2. **Host keys (D1, D2).**
   - The `HostKey` enum, then convert the keyboard classes, the
     special-key maps, overrides, layouts and diagnostics.
   - The unified input entry point, with `MainForm` reduced to
     forwarding events.
   - The `Keys` parity check and the settings/`.mzkbd` round-trip
     check.

   *Done 2026-10-24.* `HostKey` (`Hardware/`) was generated from
   `Keys` by reflection: 194 members with the same names, values and
   declaration order. The order matters because it decides which of
   two names sharing a value `ToString()` writes (`Enter`, not
   `Return`). The keyboards, special-key maps, `KeyOverride`,
   diagnostics and `KeyScript` use it. So do the keyboard editor's
   model, the settings diff and the HID diagnostic, with a cast only
   where a WinForms event arrives. The input contract is
   `IKeyboardInput`, implemented by `KeyboardMatrixBase` and exposed
   as `IMachine.KeyboardInput`. It keeps the existing method names
   (`OnKeyDown(HostKey)`, `OnKeyPress(char)`, `OnKeyUp(HostKey)`)
   rather than D2's `KeyDown`/`KeyUp`/`Text`, which saves renaming
   them in every doc comment. The PC-shift rule moved unchanged into
   the base class, and `MainForm`'s three handlers now forward one
   line each. `HostKeyParity` (`UI/`) runs at startup beside
   `MatrixValidation`. It checks member names, values and order, and
   the `ToString()` of every key code under every Shift/Control/Alt
   combination, in about 7 ms. A copy with `Enter` and `Return`
   swapped was caught. For the round-trip check, a `settings.ini`
   and a `.mzkbd` full of aliases, modifier combinations, lowercase
   and numeric names were re-saved by the old and new builds. The
   results were byte-identical apart from the `.mzkbd` timestamp
   line. Suite 27/27. The suite has no overrides, so a sandbox script
   checked them: F6 and Shift+F7 bindings typed `ABA` as expected.
3. **Audio (D4)** — `IAudioOut`; `Sound` takes it from the front
   end.
   *Done 2026-10-24.* `IAudioOut` (`Hardware/`) has the three calls
   the feed thread already made (`BufferedDuration`, `AddSamples`,
   `Reset`) plus `Dispose`. `Sound.OutputFormat` publishes the format
   and buffering the feed thread plays at (44.1 kHz, 16-bit mono,
   16 chunks of 1764 bytes), so a front end can open a matching
   output. `MainForm` opens a `WinmmWaveOut` in it and passes it to
   `Sound.Start`, which owns and disposes it as before. The feed
   thread, its pacing and the pulse-hold are untouched. `WinmmWaveOut`
   stays in `Hardware/` for now; Phase 3 leaves it in the front end.
   Suite 27/27. The suite can't hear the real-time output, so a
   scratch harness drove `Sound` through a recording `IAudioOut` that
   drains in real time. It got 1764-byte chunks paced to real time
   (56 in 1 s), a 999 Hz tone from 895 kHz / 895, one `Reset` on mute,
   nothing while muted, resumption on unmute, the output disposed
   with `Sound`, and an external-PCM ramp played in order.
   Observation, not fixed (pure refactor): one chunk (20 ms) is
   still submitted after a mute. The feed loop checks `Muted`, then
   waits for room in the queue, then submits; a pause during the wait
   flushes the device and then queues that chunk. It goes to v1.5.0
   with the other recorded bugs.
4. **Joystick (D5)** — `IJoystickSource`.
   *Done 2026-10-24.* `IJoystickSource` (`Hardware/`) has the members
   the front end already used: `Poll`, `GetCurrentButtons`,
   `SetButtonIndices` and the two button masks. `JoystickInput`
   implements it unchanged. `MainForm` holds its source as the
   interface and hands that to Settings, the button-capture dialog
   and the HID diagnostic. The machines never referenced
   `JoystickInput`; they only own the `Joystick` it writes into, so
   Phase 2's session can poll whatever source the front end supplies.
   Suite 27/27. Dump runs already skip gamepad polling (Phase 0.5),
   so the suite can't see the gamepad; a live check with a real pad
   covered it.
5. **Dialogs (D6)** — `MatrixValidation` callback.
   *Done 2026-10-24.* `MatrixValidation.RunAndLog` takes an
   `Action<string, string>` (message, then title) in place of its
   `MessageBox`, following `AutoLoadOrchestrator`'s `Action<string>`.
   `Program.cs` passes the same `MessageBox.Show` call, so the dialog
   is unchanged. Suite 27/27. The dialog only appears on drift, so a
   scratch build with one injected complaint checked it: same title,
   warning icon and text.
6. **Sweep** — temporarily set `ImplicitUsings` so that the
   WinForms/Drawing global usings drop out for core files, or

### Phase 5 — Code review pass

A full pass over the code once the new structure is in place. It
comes after Phase 4 because the WinForms app and the headless runner
are then two real users of the core, which shows what each one needs
from it. It must happen before MZRakuCLI (v1.6.0) builds on the core,
while renames still only have consumers inside this repo.

- **Names:** class and member names consistent with the new
  structure, including the session and the machine classes, and
  leftovers from when MZRaku emulated only the MZ-700.
- **Visibility:** core members that neither front end uses become
  `internal`.
- **Orphaned code:** the compiler's unused-member warnings, plus a
  reference scan for public members nothing uses.
- **Stale comments** that describe how the code used to work.

Rules:

- **Persisted names stay.** `settings.ini` keys, `.mzkbd` contents

- **Dormant on purpose is not orphaned.** Code kept deliberately,
  such as the parked MZ-80A invisible-LOAD path, is listed for a
  keep-or-remove decision; it is never deleted automatically.
- **Bugs found are recorded, not fixed**, as in the rest of v1.4.0.
- **Separate commits** for renames, visibility changes and
  deletions, with the suite after each.

## Risks

| Risk | Mitigation |
|---|---|
| `HostKey` names or flag formatting drift from `Keys`, breaking saved overrides and `.mzkbd` files | D1 parity check plus the byte-identical round-trip check |
| The keyboard's down/char ordering subtleties change behaviour | The input contract keeps today's events and order; scripted typing cases on all three machines |
| Real-time MZ-700/80A sound changes without the suite noticing | The feed thread is untouched (D4); `.snd.txt` covers register behaviour; listening check at close |
| `MainForm` extraction changes start/switch/apply ordering | Small steps, suite after each; manual checks of machine switching and Settings → Apply |
| Flaky cases erode trust in the suite | Phase 0.5 resolves or excludes them before refactoring starts |
| Large mechanical diffs hide mistakes | Phase-sized commits with the suite after each; `git mv` for moves so history and blame survive |
| The main csproj compiles `Core/` files twice | Exclude `Core/**`, as for `tools/**` and `Z80Core/**` |
| A Phase 5 rename breaks a saved file, or a removal takes out code that was dormant on purpose | Persisted names are excluded; dormant code is listed for a decision, not deleted |
