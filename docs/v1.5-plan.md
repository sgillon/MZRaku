# v1.5.0 plan — clear the decks, then features

**Status:** AGREED 2026-10-31 (all four decisions as recommended).
Phase 0 and Phase 1 done 2026-10-31.

Bug phases (0–3) planned in detail; the feature phase is outlined and
gets its own detailed plan when Phase 3 closes.

## Goal

v1.5.0 is the first packaged release since v1.3.0 and the first built
on the v1.4.0 core. It does two things, **in this order**:

1. **Clears the decks.** Every bug parked or recorded up to v1.4.0 is
   fixed, or deliberately closed with the reason written down, so
   v1.6.0 (MZRakuCLI) starts from a clean list (roadmap principle:
   "parked bugs don't outlive a feature release").
2. **Adds the UI-light features** listed in `roadmap.md`.

No feature work starts until the bug phases are closed.

### Ground rules

- **Bugs before features.** Phases 1–3 close before Phase 4 starts.
- **Fix or close, never leave open.** An investigation that runs out
  of road is closed on purpose: the finding goes in `history.md`, the
  roadmap entry is removed, and any GitHub issue is closed with a
  comment saying why.
- **A regression case for each fix a dump can show.** `--keys=` makes
  keyboard bugs scriptable. Fixes a dump can't show (real-time audio,
  dialogs) get a recorded live check instead.
- **Goldens change only on purpose.** If a fix changes an existing
  golden, the new image is approved by the user in the same step,
  with the reason in the commit.
- **Suite after every change.** `python tools/regress/regress.py`
  (windowed) and `--headless`, both all-pass, before every commit.
- **Behaviour changes are user-visible.** Unlike v1.4.0, v1.5.0 is
  allowed to change behaviour; each change is listed for the release
  notes as it lands.

## Phase 1 — Known causes

Small, contained fixes. One commit each.

**1.1 MZ-700 Insert cassette (B1).**
`Mz700Cassette.TrapReadHeader` is $0436 (WRINF, the header *write*)
and `TrapReadData` is $04D8. 1Z-013A's jump table sends RDINF
($0027) to $04D8 and RDDAT ($002A) to $04F8. So the header read hits
the data trap, which delivers both and empties the tape, and the
real data read finds nothing. `Mz800Cassette` already uses
$04D8 / $04F8.
- Fix: header trap $04D8, data trap $04F8.
- Check first: what else reaches those traps on the MZ-700 (Load
  cassette and drag-drop don't use them for machine code; confirm
  the BASIC-cassette path and S-BASIC's own LOAD don't either).
- Regression case: needs a way to *insert* (not load) a cassette from
  the command line, then type `L` with `--keys`. If that is a new
  flag, it is small and MZRakuCLI wants the same thing.
- Live check: Insert cassette + `L` on a machine-code game.

*Done 2026-10-31.* Traps moved to RDINF $04D8 / RDDAT $04F8 (checked
against the ROM's jump table). Only the monitor's `L` reaches them:
S-BASIC has its own tape code, and Load cassette / drag-drop
direct-inject. New `--insert=<path>` command-line flag (File → Insert
cassette at startup, both front ends; left out of `--help` until the
Phase 4 CLI docs) and new case `mz700_insert`: Space Panic inserted,
`L` typed, game reaches its attract screen. Suite 28/28 both ways.

**1.2 One audio chunk after mute (B2).**
`Sound`'s feed loop checks `Muted`, waits for queue room, then
submits, so a mute during the wait still queues 20 ms. Fix: check
again after the wait, before submitting.
- No dump can show it; live check: pause during a held MUSIC note
  and during the boot tone, on the MZ-700 and MZ-80A.

*Done 2026-10-31.* Both feed paths (square wave and the MZ-800's
external PCM) check `Muted` again after the wait. Live check passed.

**1.3 Settings change summary labels (B3).**
`SettingsDiff.VkLabel` (`UI/Settings/SettingsDiff.cs:444`) reads the
MZ-700's labels for every machine. `MzKeyEditorForm.VkLabel` already
takes the machine's `IKeyboardEditorContext`; pick the label table by
machine the same way.
- Live check: an MZ-80A Home override reads "PC Home (CLR/HOME)", an
  MZ-800 F11 reads "PC F11 (GRAPH)".

*Done 2026-10-31.* `DescribeKeyOverrides` takes the machine's
`*SpecialKeyMap.Labels`. Live check passed.

**1.4 MZ-80A layout validation (B4).**
`MatrixValidation.RunAll` checks the MZ-700 and MZ-800 layouts, not
the MZ-80A's.
- First run `Mz80aKeyboardLayout.Validate` on its own and look at
  what it reports. Fix any real drift; if it reports false positives,
  fix the check.
- Then add the call, so a clean startup stays silent.

*Done 2026-10-31.* On its own it reported nothing, so the call went
straight into `MatrixValidation.RunAll`; startup stays silent.

**1.5 MZ-80A PIT counter 0 rate (B5).**
`MZ80A.AccumulatePit` counts C0 at 895 kHz (the MZ-700's rate, "never
confirmed for the MZ-80A"); the sound path at the end of `RunFrame`
takes 1 MHz, which matches measured MUSIC pitch.
- Confirm C0's clock from the MZ-80A service manual (your local copy;
  the same check that settled C1 at 31.5 kHz in 2026-07).
- Make the counter and the sound path use the one confirmed rate.
- The MZ-80A MUSIC cases in the suite would show any pitch change.

*Done 2026-10-31.* The service manual's CPU board schematic (IC47
8253) answers it without guesswork: CLK0 is the 2 MHz line, OUT0
clocks an LS74 wired as a ÷2 toggle (IC48) before the SOUND buffer,
GATE0 is the $E008 D0 latch, CLK1 is 31.5 kHz and OUT1 only clocks
counter 2. So C0 now counts one tick per CPU cycle, and the sound
path's "1 MHz" is right as 2 MHz ÷ 2 (the old comment put the ÷2 before
CLK0). $E004 can't be read back, so nothing else moves; suite 28/28.
Recorded, not changed: the sound path's counter-1 fallback (for MC
games that program counter 1) is empirical, since OUT1 doesn't reach
the speaker on the schematic.

## Phase 2 — Unknown causes

Investigations. Each gets a time box (see Decisions); if it runs
out, the item is closed as described in the ground rules.

**2.1 Keyboard dead after Settings Apply (B6).**
Didn't reproduce from fresh settings in v1.1.0, v1.3.0 or the v1.4
work (2026-10-24), so the trigger is something those runs lacked.
- Reproduce with a **copy of your real `settings.ini`** in a sandbox
  (first suspect: existing `[CharMap]` / `[KeyOverrides.MZ700]`
  entries). Then try the other suspects: a debug pane open (Keyboard
  Matrix, HID diagnostic), full-screen, capturing a modifier key, a
  long session.
- Once it reproduces: instrument rather than bisect. Log the matrix
  rows, held keys, pending downs and staged bits around the Settings
  close.
- If it reproduces with a script, it becomes a regression case.

*Done 2026-10-31.* Not the settings at all: the real `settings.ini`
has no overrides. The trigger is the shortcut that opens the dialog.
Ctrl+Shift+K's Ctrl and Shift key-downs reach the MZ keyboard (Ctrl is
MZ CTRL), the K opens the modal Settings dialog, and the dialog takes
the key-ups, so MZ CTRL (and SHIFT) stayed held: letters became
control codes until Ctrl+R's ReleaseAll. The fresh-settings runs went
in through the menu with the mouse, so nothing was held. The old
bisect's c702bb7 (Settings deep-link) was right after all: it added
the Ctrl+Shift+letter shortcuts. Any focus loss with a key down (Ctrl+O's
file dialog, Alt+Tab) did the same, on all three machines. Fix:
`IKeyboardInput.ReleaseHeldKeys()`, called from `MainForm.Deactivate`
through `EmulatorSession.ReleaseHostKeys()`. It releases only the
host's holds, not the auto-typer's bits, and is skipped in `--dump`
runs. No regression case: the suite can't open a modal dialog.

**2.2 MZ-700 sound loose ends (B7).**
Concrete case from v1.4 Phase 0.3: the boot tone's 138-cycle
hard-gate pulse comes before C0's reload is handed over at frame
end, so whether it sounds depends on the feed thread's timing.
- Make the pulse audible deterministically (hand the reload over at
  the gate edge, or hold the pulse until the reload arrives).
- The suite's `.snd.txt` traces show the event order; the sound
  itself needs a live ear check.
- Scope: see Decisions.

*Done 2026-10-31.* Not a sound-path timing problem. The boot tone is
`+A0` played by the monitor's melody routine ($0577 → MELDY at $01C7),
which starts the note (MSTA $02AB), waits 4 tempo periods at $02C8,
then stops it (MSTP $02BE). $02C8 was trapped as a "press PLAY /
check BREAK" tape wait and returned at once, so every note the
monitor's melody routine plays was cut to ~138 cycles. Only MELDY
calls $02C8 in 1Z-013A, and the trap's last job (getting SAVE out)
went in 2.6, so the trap is removed: the boot tone now lasts ~120 ms
and spans the reload handover. That exposed a second problem:
`MonitorReady` keyed on the banner, which the ROM prints *before* the
tone, so `--basic` injected BASIC mid-note and left the gate open. It
now also waits for the `*` prompt printed after the tone (display code
$6B; the old comment's `*=$2A` was the `-`). All nine MZ-700 goldens
re-approved: PNGs unchanged except `mz700_panic` (aliens elsewhere,
play starts ~6 frames later); sound logs differ only in the boot tone.
Suite 30/30. Live check: the boot tone is clearly audible, and
machine-code games that play notes through the monitor's MELDY now
have sound they were silently missing.

**2.3 Font Sheet GRAPH click-to-type on the MZ-700 (B8, #3).**
The click lands the right byte but leaves the attribute at bank 0. A
PC keystroke on the same matrix slot in GRAPH mode works.
- Find the cursor-position RAM address first, so a diagnostic can
  read the typed byte and attribute directly (the old VRAM diff was
  drowned by the cursor blink).
- Then find what state the PC-keystroke path sets that the
  auto-typer's press doesn't (S-BASIC's input handler, loaded from
  1Z-013B, and the monitor's GRAPH mode flag at $1170).
- Done before Phase 4's MZ-800 Font Sheet click-to-type, which is
  likely to meet the same problem.
- Regression case: `--keys` can't click, so this needs the
  equivalent auto-type request scriptable, or a live check only.

**2.4 MZ-80A invisible LOAD (B9).**
Polish only: the typed LOAD + RUN path works. Direct inject plus the
$4E4E variable-table fix-up still gave Error 16 on `GOSUB`.
- Snapshot RAM after the failed auto-RUN and after a successful
  manual RUN, and diff. Suspects from 2026-07: $2D74, $1172/$117C,
  $5051–$5052.
- If found: switch to the invisible path and drop the typed one.
  If not: close it and keep typed LOAD (and remove the scaffolding).

**2.5 MZ-700 Insert cassette for S-BASIC's LOAD (B12).**
Found in the 1.1 live check: a BASIC cassette inserted with Insert
cassette isn't read by `LOAD` typed in S-BASIC. S-BASIC banks the
monitor ROM out and uses its own tape code, so the monitor traps
fixed in 1.1 never fire (the status text already says "Type L in
Monitor mode"). Load cassette and drag-drop work because they
direct-inject.
- Find S-BASIC's tape-read entry points (header and data), the way
  the SAVE trap at $0D47 was found: pause the debugger while `LOAD`
  waits for the tape, then read the routine.
- Trap them with the ROM banked out, as the SAVE trap does, and
  deliver the queued image. Then BASIC programs and data files load
  as they would from a real tape.
- Regression case: `--insert=` a BASIC program, `--basic`, type
  `LOAD` then `RUN`.

*Done 2026-10-31.* A scratch harness dumped RAM while `LOAD` waited;
the stack showed the call chain. S-BASIC keeps a jump table at the
monitor's vectors: $0021 → $0A3B / $0024 → $0A3F (write header /
data), $0027 → $0A7A / $002A → $0A7E (read header / data), $002D →
$0A94 (verify). The reads take HL = destination and BC = count and
exit through $0A71 (clear $0050, CY=0, EI). `Mz700Cassette` now traps
$0A7A and $0A7E with the ROM banked out, after checking the entry
bytes are 1Z-013B's, and serves the inserted image the same way the
monitor traps do. New case `mz700_insert_basic`: Dragon Caves (29 KB,
crosses $D000) inserted, `LOAD`, `RUN`, title screen. Suite 29/29.

**2.6 MZ-700 S-BASIC SAVE on its real write entries (B13).**
The SAVE trap at $0D47 is S-BASIC's tape bit-delay loop, not a
"press RECORD" wait: it fires on every tape access, so `LOAD` with no
cassette shows "Save skipped: header … size=0", and SAVE gets back to
Ready only because the BreakWait trap then forces BREAK.
- Trap S-BASIC's write entries instead (found in 2.5): $0A3B writes
  the header and $0A3F the data, each from HL for BC bytes. Capture
  the header, then write the `.mzf` on the data write, and return
  success through the routine's exit, so SAVE ends at Ready normally.
- Remove the $0D47 trap and the forced BREAK.
- Regression case: type a short program, `SAVE "NAME"`, then check
  the screen is back at Ready and the `.mzf` is byte-correct.
- The template for Phase 4's MZ-800 BASIC SAVE.

*Done 2026-10-31.* One trap at $0A67, the write body both entries
reach after BASIC has printed "WRITING <name>" and passed the motor
check (entry bytes checked first). E says which block: the header is
kept, the data block completes the `.mzf`, and each returns through
the routine's own exit (DE popped, $0050 cleared, CY=0, EI). The
$0D47 trap, the $0FFC header guess and the forced BREAK are gone. The
saved file is byte-identical to the old trap's, SAVE now ends at
Ready, LOAD with no cassette no longer says "Save skipped", and the
file loads back (`Found` / `LOADING`, `LIST`). New `save` artefact in
`regress.py` (the sandbox's `saves/*.mzf`, compared byte for byte) and
case `mz700_save`. Suite 30/30.

## Decisions

To agree before Phase 1:

1. **Order within the bug phases** — known causes (Phase 1) before
   investigations (Phase 2). *Recommended:* quick, certain wins
   first, and a clean suite baseline for the harder work.
2. **Time box for investigations** — roughly one session each for
   B6–B9 before the fix-or-close call, which you make.
3. **MZ-700 sound loose ends scope** — the boot-tone pulse only,
   unless you have other imperfect timings in mind (name them and
   they join 2.2).
4. **Known limitations** — MZ-800 border, floppy / QD / printer and
   the v1.0.x upgrade path stay limitations, not v1.5.0 bugs.

Decided at Phase 3: #2 and #4 outcomes.
