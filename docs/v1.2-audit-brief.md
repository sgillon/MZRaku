# v1.2.0 audit — Stage 1 brief

This document is the **contract** for the v1.2.0 codebase audit.
Stage 2 (audit + plan) reads this and produces findings + a fix
plan. Stage 3 (review + execute) reads Stage 2's outputs and applies
them per-finding.

The brief is deliberately prescriptive on discipline (categorisation,
output schemas, exit states) and permissive on judgment
(what-to-look-for, how-deep-to-go). If Stage 2 makes a judgment call
the brief doesn't cover, it should state the call and move on rather
than back-solve to fit imagined intent.

## Purpose

v1.2.0 is a **codebase audit + resulting refactors + MZRaku-side
test seed release**, not a feature release. The goal is to reduce
the accumulated debt of ~15 months of prototype-shaped development
so that subsequent feature arcs (Avalonia port, MZ-800, MZ-80K/B)
start from a cleaner base.

v1.1.0 was tagged 2026-08-22 with full MZ-80A Settings-dialog
parity delivered. The `docs/release-check.md` walk passed cleanly
against v1.1.0, so the audit begins from a known-passing baseline.

## Scope

**In scope:**
- All MZRaku source under `Hardware/`, `UI/`, and the repo root
  (`MainForm.cs`, `MZ700.cs`, `MZ80A.cs`, `Program.cs`,
  `Settings.cs`).
- The csproj (`MZRaku.csproj`) and project structure.
- Docs that are actively load-bearing: `docs/usage/*.md`, `README.md`,
  `docs/release-check.md`. History docs (`docs/history.md`,
  `_journal/*`) are informational, not audit targets.

**Out of scope (hard rules):**

1. **`Z80Core/**` is out of scope by construction.** The Z80 core
   lives in a separate repo (`sgillon/Z80Core`), consumed here as
   a git submodule. Deliberately atomic; treated as a third-party
   dependency for this audit's purposes. Stage 2 discovery must
   not walk `Z80Core/**` at all. Any finding that describes
   Z80Core behaviour is out-of-scope by construction and must be
   dropped without categorisation. Rationale: keeps Z80Core as a
   constant during MZRaku testing (regressions during MZRaku audit
   validation are provably not Z80Core changes), and lets Z80Core
   get its own three-stage audit later.
2. **New features.** All feature work belongs elsewhere per
   `[[project-roadmap]]`. If Stage 2 surfaces a feature-shaped
   idea that's too good to defer, it may propose it as a
   category-(b) finding with an explicit "feature-shaped
   exception" tag — Stage 3 will apply extra scrutiny before
   accepting.

## Hard rule: no code changes during Stages 1 and 2

Stage 3 is the only stage that touches code. Ad-hoc fixes during
audit — even trivial-looking dead-code deletions, comment
corrections, or single-line clean-ups — are **not permitted** and
must be added as findings instead, however small.

Rationale: the categorisation + per-finding review discipline is
what keeps v1.2.0's scope bounded. "Clean the deck" releases
routinely balloon into rewrites via ad-hoc fixes; that failure mode
is the specific thing this rule prevents.

Corollary: Stage 2 may produce a "cleanup batch" finding that
groups many trivial fixes (e.g. "delete these 12 unused private
methods surfaced by Roslyn"), but the batch is still a finding
that Stage 3 accepts, modifies, or rejects — not a fait accompli.

## Model configuration

- **All-Opus.** Stage 1 (this brief) produced by Opus; Stage 2
  (audit + plan) by Opus; Stage 3 (review + execute) by Opus.
  Matches the whole-project cadence to date.

Recording so future audits (of Z80Core, of a v2.x sweep) can
compare against the multi-model alternative if we want the
comparison later.

## Audit ethos

**Deliberately harsh on ourselves. YAGNI-first.** The default
answer to "should this stay?" is "no". Only override when one of
two things applies:

1. **Legibility for learning purposes.** MZRaku is also a vehicle
   for Steve's re-engagement with software development. Code that
   exists to make a concept legible earns its keep even where a
   production codebase would inline it. Named clearly, this is
   **"code as documentation of what the machine is doing"** — a
   variable, method, or helper class that survives on YAGNI
   grounds because it helps a reader understand the *hardware*
   or *architecture*, not just the code path.
2. **Future maintainability.** Items with a specific placement in
   `[[project-roadmap]]` can stay as scaffolding — but **only if
   the placement is real and near-term (v1.3.0 or v1.4.0)**, NOT
   aspirational. "Might one day want to..." is not justification.

Reflex during the audit: reach for `git rm` before reaching for a
comment explaining why something's staying. If keeping something
needs an explanation, that's already a signal it may not warrant
keeping.

## Categorisation

Every finding is placed into exactly one of three categories:

| Category | Meaning | Expected count |
|---|---|---|
| **(a) Critical** | Release blocker discovered post-tag. Warrants a v1.1.1 hot-fix on its own, not bundled into v1.2.0. | 0, hopefully. |
| **(b) v1.2.0 target** | Real technical debt or inconsistency worth fixing in this release. Drives v1.2.0's fix phases. | Bulk of findings. |
| **(c) Longer-arc parked** | Genuinely defer-worthy. Goes into `[[project-feature-backlog]]` or its own memory file. | Modest — most items should categorise as (b) or drop entirely. |

Categorisation is load-bearing. Getting it right is what keeps
v1.2.0 from ballooning. When in genuine doubt, prefer (c) —
deferring a real item is cheaper than shipping a rushed fix.

**Findings that fail both softening considerations should not be
recorded at all** — they're just "code the audit disagrees with
that has no justification for change or preservation". Drop
silently rather than fill up the findings doc.

## Per-finding output schema (Stage 2 MUST follow)

Each finding is a distinct markdown section in
`docs/v1.2-audit-findings.md`, following this exact schema:

```markdown
### F-NNN — <short title>

**Category:** (a) / (b) / (c)
**Area:** Hardware / UI / MainForm / Settings / Project structure / Docs
**Files:** `path/to/file.cs:LINE-LINE`, ...
**Effort estimate:** trivial / small / medium / large

**What's there today.** Factual, no editorialising. What does the
code do, how is it structured, why does it exist.

**Why it warrants a change.** The finding itself. Concrete —
"this method is 320 lines and mixes three concerns" beats "this
is hard to read".

**Proposed change.** Specific, actionable. If the finding is (a)
or (b), Stage 3 will apply this or a modified variant. If (c),
this describes what a future release would do.

**Justification against the three axes** (required for every
finding — Stage 3 rejects findings missing any axis):

- **Pros vs. cons against the code itself.** Concrete impact —
  file count delta, LOC delta, cyclomatic complexity change,
  runtime behaviour change (should be none for a refactor).
- **Impact on legibility for learning purposes.** How does this
  change affect a reader's ability to understand what the
  machine is doing? If neutral, say so explicitly.
- **Impact on future maintainability.** How does this change
  affect the roadmap's next steps (v1.3.0 polish arc, v1.4.0
  MZ-800 arc, v2.0.0 Avalonia port)? If neutral, say so
  explicitly.

**Related findings.** Cross-refs to other F-NNN entries this
interacts with or depends on.
```

Findings numbered `F-001`, `F-002`, ... in order of appearance in
the doc (not category order — category is a field). Stable
numbering matters: Stage 3 references findings by number in
commit bodies.

## Stage 3 review rubric (findings will be tested against this)

Stage 3 reads each finding and applies four gates:

1. **Is Stage 2 reversing a deliberate design for premature
   optimisation?** Deliberate designs live in memory files and
   commit-body comments; if a finding proposes reversing one, the
   finding needs to acknowledge and address the original
   reasoning.
2. **Does the "legibility for learning" argument stand
   independently, or is it retrofit to justify a nice-to-have?**
   Legibility must be intrinsic — the reader understands the
   machine better because of this code. Not "someone might find
   it interesting" or "it's a nice example of X".
3. **If invoking "future placement", does it name a real
   `[[project-roadmap]]` entry with a version — not a vibe?**
   Aspirational placements are not justification.
4. **Has the pro/con weighing stacked the deck?** If cons are
   trivially dismissed or omitted, the finding is flawed even if
   the underlying intuition is correct.

Three exit states per finding (not two):

- **Accept + execute** — apply the change, restating justification
  in the commit body.
- **Accept with modifications** — apply a modified change,
  documenting the divergence from Stage 2's proposal in the
  commit body.
- **Reject** — no change, rationale line preserved in the
  findings doc for future audits.

Adversarial posture is required. "Seems reasonable" is the
failure mode to guard against — this is single-model Opus doing
both Stage 2 and Stage 3, so there's no built-in fresh-eyes
effect from a model swap. The rubric above compensates by making
the review mechanical (does this finding pass all four?) rather
than judgment-drift-prone.

## Stage 2 mechanism

Stage 2 runs a **multi-agent fan-out over codebase areas**, then
consolidates, then runs a **supporting `code-review` skill pass**
at high effort to catch anything the broader-lens audit missed.

### Fan-out partition

The codebase splits into six areas. Each area runs its own
concurrent audit agent, producing area-scoped findings against
the per-finding schema above.

1. **Hardware — MZ-700 side.** Everything under `Hardware/` that
   isn't `Mz80a*.cs` or MZ-80A-specific: `CharMap.cs`,
   `CharMapOverrides.cs`, `Cassette.cs`, `CassetteFile.cs`,
   `IoBus.cs`, `Keyboard.cs`, `KeyboardDiagnostics.cs`,
   `KeyboardMapFile.cs`, `KeyOverride.cs`, `MatrixCoverage.cs`,
   `MatrixValidation.cs`, `MZ700Memory.cs`, `Mz700MatrixReference.cs`,
   `Mz700SoundReference.cs`, `MzGlyphCatalog.cs`,
   `MzKeyboardLayout.cs`, `PcKeyIndex.cs`, `Pit8253.cs`,
   `Ppi8255.cs`, `RomKeyTables.cs`, `Sound.cs`, `SpecialKeyMap.cs`,
   `Video.cs`, `WinmmWaveOut.cs`, `Joystick.cs`, `JoystickInput.cs`,
   `IKeyboardMatrix.cs`, `IMachine.cs`, `MachineType.cs`,
   `PcKeyIndex.cs`.
2. **Hardware — MZ-80A side.** All `Hardware/Mz80a*.cs` files:
   `Mz80aCassette.cs`, `Mz80aCharMap.cs`, `Mz80aCharMapOverrides.cs`,
   `Mz80aIoBus.cs`, `Mz80aKeyboard.cs`, `Mz80aKeyboardLayout.cs`,
   `Mz80aMatrixReference.cs`, `Mz80aSpecialKeyMap.cs`,
   `Mz80aVideo.cs`, plus `Hardware/MZ80AMemory.cs`.
3. **UI/Keyboard.** All editor forms + shared abstractions
   introduced in Phase 5.5: `AdvancedKeyboardForm.cs`,
   `IKeyboardEditorContext.cs`, `IPhysicalKeyboardLayout.cs`,
   `KeyBindingEditorForm.cs`, `KeyboardMatrixForm.cs`,
   `KeyboardMatrixGrid.cs`, `KeyCaptureControl.cs`,
   `Mz700KeyboardEditorContext.cs`,
   `Mz700PhysicalKeyboardLayout.cs`, `Mz80aKeyboardEditorContext.cs`,
   `Mz80aPhysicalKeyboardLayout.cs`, `MzKeyboardDiagram.cs`,
   `MzKeyEditorForm.cs`, `VkBindingEditorForm.cs`.
4. **UI/Diagnostics + UI/Debugger.** `FontSheetForm.cs`,
   `HidDiagnosticForm.cs`, `SoundDiagnosticForm.cs`,
   `DebuggerForm.cs`, `MemoryViewer.cs`, `Z80TestRunner.cs`
   (host-side pieces of the runner — Z80Core parts are
   out of scope).
5. **UI/Settings + UI root.** `SettingsForm.cs`,
   `SettingsSnapshot.cs`, `SettingsDiff.cs`, `AboutForm.cs`,
   `SmoothControls.cs`.
6. **Top-level + project structure.** `MainForm.cs` (largest single
   file, own area), `MZ700.cs`, `MZ80A.cs`, `Program.cs`,
   `Settings.cs`, `MZRaku.csproj`, project file layout / folder
   organisation itself.

Each fan-out agent:
- Reads its assigned files.
- Also reads (but does not re-audit) other areas' interfaces at the
  method-signature level, so cross-area findings can reference the
  right symbols.
- Emits findings using the schema above, numbered locally
  (`FH1-001`, `FH1-002` for area 1; `FH2-001` for area 2; etc.).
  Consolidation renumbers to global `F-NNN`.

### Consolidation

After the six fans complete, a consolidation pass:
- Merges area findings into a single `docs/v1.2-audit-findings.md`,
  renumbering to global `F-001` .. `F-NNN`.
- De-duplicates findings raised in multiple areas (e.g. a
  parallel-machine-class pattern showing up in Hardware MZ-700
  side and Hardware MZ-80A side).
- Cross-links related findings.
- Produces a companion `docs/v1.2-audit-plan.md` that groups the
  category-(b) findings into ordered fix phases, drafted the same
  way v1.1's phase plan was — each phase self-contained, testable,
  buildable + smoke-testable on both machines before the next
  starts.

### Supporting `code-review` pass

After consolidation, a single `code-review` skill run at `high`
effort scope-limited to the in-scope areas above. Its findings
merge into the consolidated doc with the `F-CR-NNN` prefix so
they're distinguishable from the fan-out ones. This catches
correctness bugs and reuse/simplification opportunities that the
broader-lens audit lens may miss.

Skip anything `code-review` surfaces that's Z80Core-side, per the
hard rule.

## Seed areas — pointers, not a hunt list

Stage 2's fan-out does its own discovery. This list exists so
obvious things aren't missed by chance, not as a checklist to be
worked through mechanically. Findings NOT in this list are equally
welcome; findings in this list may on inspection turn out to be
non-issues.

**Structural:**

- Parallel machine classes with converged shape (`Cassette` ↔
  `Mz80aCassette`, `CharMap` ↔ `Mz80aCharMap`,
  `Mz700MatrixReference` ↔ `Mz80aMatrixReference`,
  `MzKeyboardLayout` ↔ `Mz80aKeyboardLayout`). Extraction
  candidates: shared interfaces, common base classes, or
  parameterised data.
- `if (_machine != null) ... else if (_mz80a != null)` branching
  in `MainForm`. v1.1 Phase 5.5 showed the
  `IKeyboardEditorContext` pattern collapses some cleanly; audit
  whether the same treatment applies to Sound Diagnostic and
  Keyboard Matrix panes (still MZ-700-only).
- `IMachine` surface — currently ~65 lines. Some `MainForm`
  branches could collapse behind additional `IMachine` methods
  (Sound / Cassette / Keyboard / Video stay concrete today).
  Assess net gain vs. added abstraction cost.
- File organisation — `Hardware/` has 30+ files with no
  per-machine grouping. `Hardware/MZ700/` and `Hardware/MZ80A/`
  sub-folders would make convergence points more visible. Assess
  churn vs. clarity trade.

**Cleanup:**

- Dormant scaffolding: invisible-LOAD path in `Mz80aCassette`
  (see `[[project-mz80a-cassette-autorun]]`); pointer-hunt
  diagnostic `DumpMz80aBasicPointerCandidates` in `MainForm.cs`;
  any `// removed` / stale TODO comments.
- Unused fields / methods — Roslyn analyzers will surface these
  mechanically.
- Comment / doc pass — audit XML doc comments for accuracy
  after MZ-80A landing + v1.1 Phase 5. Some header comments still
  reference in-flight-phase status.
- `internal` vs `public` visibility — `WinmmWaveOut` is
  `internal sealed`; `Sound` is `public sealed`. Audit for
  consistency and least-privilege.
- `Ppi8255` bit-name events (`SpeakerGateChanged`,
  `MotorChanged`, `IntMaskChanged`) publish MZ-700 semantics.
  Flagged in the MZ-80A landing plan as "revisit if it gets
  confusing".

**Carried forward from v1.1 as fix-forward candidates:**

- `[[project-v1-1-apply-keyboard-regression]]` — parked bug from
  v1.1 Phase 5.5a. Documented workaround (Ctrl+R after
  Settings-Apply) ships in v1.1. Natural v1.2 opportunity: while
  the audit is touching keyboard code, add the instrumentation
  the regression memory suggests (log matrix state around
  Settings-close; log `_holds` state) and fix forward when the
  mechanism reveals itself.
- MZ-80A diagram PC-key labels + red unreachable-essential
  outline — deferred from v1.1 Phase 5.5c. `PcKeyIndex` is
  MZ-700-specific; extending to MZ-80A is v1.2 polish that pairs
  naturally with the parallel-machine-classes work above.
- `.mzkbd` export / import on MZ-80A — file format currently
  MZ-700-only. Design call at audit time.

**Retired items (do NOT rediscover)** — shipped or superseded
during v1.1; recorded so the audit doesn't spend time here:

- INI `[CharMap]` per-machine split — done by v1.1 Phase 5.1
  (`[CharMap.MZ80A]` alongside `[CharMap]`).
- Settings dialog upgrade sweep (`[[project-settings-dialog-upgrade]]`)
  — retired by v1.1 Phase 5.5. Audit should confirm retirement was
  clean but does NOT re-open the scope.
- HID Diagnostic MZ-80A support — done by v1.1 Phase 4a.
- Font Sheet MZ-80A support — done by v1.1 Phase 5.4 (view-only).

## Test seed (Phase C — parallel to audit)

Sits outside the audit loop — it's a build-out, not a finding to
be reviewed. Executes directly against this brief, either
concurrently with Stage 2 or after Stage 3.

**MZRaku.Tests/** — small host-side xUnit project. Coverage targets:

- CharMap lookups (MZ-700 + MZ-80A).
- KeyOverride INI round-trip (write, re-read, expect equivalence).
- Settings INI round-trip including v1.1's per-machine sections
  (`[CharMap.MZ80A]`, `[KeyOverrides.MZ80A]`, `[DebugPanes]`,
  `[Display.MZ80A]`, `[Keyboard.MZ80A]`).
- Mode-flag bit math for MZ-700 `$0060 & $10` and MZ-80A GRPH.
- `Mz700MatrixReference.Validate()` and
  `Mz80aMatrixReference.Validate()` — both currently fire at
  boot; a test asserting empty complaint lists guards the
  reference data across future edits.
- `Mz80aCharMap.Validate()` and `SpecialKeyMap.Validate()` /
  `Mz80aSpecialKeyMap.Validate()` — same rationale.

Runs as a release-check step, not per-commit CI (single-dev
cadence).

**Z80Core testing** — deferred to the eventual Z80Core-repo audit
per the hard-rule exclusion. When that audit runs it should
include the `Z80Core.Tests/` project (ZEXDOC/ZEXALL exerciser
lifted from `Z80TestRunner.cs` + regression canaries + disassembler
golden tests). Not v1.2.0's scope.

## Handoff — what Stage 2 produces

After Stage 2 completes, this repo should contain:

- **`docs/v1.2-audit-findings.md`** — every finding, numbered
  `F-001` .. `F-NNN`, in the per-finding schema above. Full
  detail; this is the audit's record.
- **`docs/v1.2-audit-plan.md`** — category-(b) findings grouped
  into ordered fix phases. Each phase has a summary, expected
  effort, list of contained findings, and any dependencies on
  other phases. Category-(a) findings (if any) surface at the
  top as immediate hot-fix items. Category-(c) findings surface
  at the bottom for reference / memory placement.

Both docs get committed as they're produced. Stage 3 reads them
and applies findings per the review rubric above.
