# v1.6.0 plan — .NET 10, then MZRakuCLI

**Status:** DRAFT 2026-11-17. Phase 0 (move to .NET 10) agreed
2026-11-17; the phases after it are outlined from `roadmap.md` and
planned in detail when Phase 0 closes.

## Goal

v1.6.0 adds MZRakuCLI, a second front end on the v1.4.0 core: one bare
SDL window for Windows, macOS and Linux, driven by the command line and
`settings.ini`, shipped alongside the WinForms build (see `roadmap.md`).

Before any cross-platform work, the whole solution moves from .NET 8 to
.NET 10, so MZRakuCLI is built and tested on the runtime it ships on.
.NET 8 and .NET 9 reached end of support on 2026-11-10; .NET 10 is the
current LTS release, supported to November 2028. .NET 11 (STS, also
released 2026-11-10) has a similar end date but offers nothing MZRaku
needs, and LTS is the conventional choice.

### Ground rules

Carried over from v1.5.0:

- **Suite after every change.** `python tools/regress/regress.py`
  (windowed) and `--headless`, both all-pass, before every commit.
- **Goldens change only on purpose.** A changed golden is approved by
  the user in the same step, with the reason in the commit.
- **Persisted names stay.** `settings.ini` keys and sections, the
  comments Settings.Save writes, `.mzkbd` contents, HostKey names and
  MachineType values don't change.

## Phase 0 — Move to .NET 10

Agreed 2026-11-17. Shipped on its own as **v1.5.1** (no new features)
once done: v1.5.0's framework-dependent zip needs the .NET 8 runtime,
now out of support, and the rest of v1.6.0 is a long arc.

### Trial (2026-11-17, scratchpad copy, repo untouched)

- Only the .NET 10 SDK is installed (10.0.403); it has been building
  the `net8.0` targets all along.
- Core, MZRakuHeadless and Z80Core retargeted with no code changes;
  headless suite 45/45.
- The app gave 5 errors, all **WFO1000** (a new WinForms analyser rule:
  public properties on custom controls must say how the designer
  serializes them). All five are runtime-only properties on keyboard
  editor controls: `KeyboardMatrixGrid.ShowCoverage`,
  `KeyCaptureControl.Capturing` and `.SpecialKeyLabels`,
  `MzKeyboardDiagram.PcKeyLabels` and `.UnreachableKeyIds`.
  `[DesignerSerializationVisibility(Hidden)]` on each gave 0 warnings,
  0 errors.
- The windowed suite stopped at the **HostKey startup check** in every
  instance (the box waits for OK, so cases ran into their timeouts).
  Values still match `Keys`, but WinForms 10 swapped the declaration
  order of three alias pairs in `Keys`, so `Keys` formats them with the
  other name. `HostKey`, which is what saved names come from, formats
  them the same on both runtimes (corrected 2026-11-21; the first
  version of this table had 0xE2 the wrong way round):

  | Value | `HostKey`, .NET 8 and 10 | `Keys`, .NET 8 | `Keys`, .NET 10 |
  |---|---|---|---|
  | 0xC0 | `Oem3` | `Oem3` | `Oemtilde` |
  | 0xDE | `Oem7` | `Oem7` | `OemQuotes` |
  | 0xE2 | `OemBackslash` | `OemBackslash` | `Oem102` |

  The check also reported the combined-modifier strings built from
  those values (e.g. `Oemtilde, Shift`), 340+ in all. The headless
  runner never shows the box, which is why it passed.

### Steps

1. **Key names that don't depend on WinForms.** Survey (2026-11-21):
   names are written only by `KeyOverride.SerialiseLines`
   (`settings.ini` `[KeyOverrides.*]` and `.mzkbd`), which formats
   `HostKey`, never `Keys`; they are read by `Enum.TryParse<HostKey>`
   (overrides, `.mzkbd`, `--keys`), which already accepts every name of
   a value. The HID Diagnostic, Settings change summary and binding
   editor format `HostKey` too. Only the startup check and the capture
   banner's fallback used `Keys` formatting. Changes, on .NET 8:
   - `HostKeyParity` compares names and values as sets, not
     declaration order or `ToString()`.
   - New `Core/Host/HostKeyNames`: pins the saved name of all 16
     values with more than one name (.NET documents that `ToString()`
     may pick any of them) and fails if the runtime disagrees or a new
     shared value appears unpinned. Run by the app and the headless
     runner.
   - In `--dump` runs the startup checks warn on stderr instead of a
     dialog, so the windowed suite can't stop on one again.
   - The capture banner formats through `HostKey`.
   Saved `settings.ini` and `.mzkbd` files are unchanged.
2. **Retarget** `MZRaku.csproj` (`net10.0-windows`),
   `Core/MZRaku.Core.csproj`, `tools/MZRakuHeadless`,
   `tools/MzfBuilder` and `tools/RomAnalyse` (`net10.0`), with the
   WFO1000 attributes. `regress.py`'s `BUILD` and `HEADLESS_BUILD`
   paths follow. Build 0 warnings, 0 errors; the XML-doc check stays
   clean.
3. **The user's bin folder.** Build output moves from
   `bin\Debug\net8.0-windows` to `bin\Debug\net10.0-windows`. The user
   copies their ROMs, games and settings across; Claude doesn't touch
   them.
4. **Verify.** Headless and windowed suites 45/45 (windowed only after
   step 1, so nothing stops at the check's box). Live: start-up on all
   three machines, a keyboard override using one of the three keys
   saved and reloaded, `.mzkbd` export / import.
5. **Docs and packaging.** README (runtime link and Desktop Runtime
   version, build instructions), `release-check.md`,
   `docs/developer/architecture.md`; the small zip becomes
   `MZRaku-<version>-dotnet10.zip`. Release notes say the small zip now
   needs the .NET 10 Desktop Runtime; the standalone zip needs nothing.
6. **v1.5.1.** Release check, version bump, history, tag, GitHub
   release with both zips.

**Z80Core** is a separate repo and stays on `net8.0` for now: a
`net8.0` library runs inside a .NET 10 app on the .NET 10 runtime. Its
own retarget (library and ZexHarness sample) is a later small Z80Core
release.

## After Phase 0 — decisions to agree

From `roadmap.md`, to plan in detail when Phase 0 closes:

1. **Test strategy** (first, because it shapes the rest). Linux: WSLg
   for hands-on checks, Ubuntu CI for automation. macOS: GitHub Actions
   runners (arm64 and x64) for build, headless suite and the SDL front
   end under `SDL_VIDEODRIVER=dummy` / `SDL_AUDIODRIVER=dummy` with a
   `--dump` mode, so the same goldens run through it; a real Mac for
   window, keyboard and audio feel (preview-build testers, a cloud Mac,
   or hardware).
2. **Keyboard rework scope.** The roadmap's first phase: a
   front-end-neutral input layer built on the map in
   `docs/developer/keyboard.md`, designed with Mac keys in mind (Cmd
   against Ctrl, Option, no Insert, system F-keys).
3. **SDL binding and packaging.** Which .NET SDL library; native
   libraries per OS; an `.app` bundle and Gatekeeper on macOS (signing
   and notarisation, or documented quarantine removal); where
   `settings.ini` lives inside an `.app`.
4. **MZRakuCLI's first-release scope.** Which flags, hotkeys and
   on-screen messages, against the WinForms build.
