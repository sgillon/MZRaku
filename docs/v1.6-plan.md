# v1.6.0 plan — .NET 10, then MZRakuCLI

**Status:** DRAFT 2026-11-17. Phase 0 (move to .NET 10) agreed
2026-11-17, done and shipped as v1.5.1 on 2026-11-21; the phases after
it are outlined from `roadmap.md` and planned in detail next. All four
decisions that shape the MZRakuCLI phases (test strategy, keyboard
rework scope, SDL binding and packaging, first-release scope) agreed
2026-11-22; the phases themselves are planned next.

## Goal

v1.6.0 adds MZRakuCLI, a second front end on the v1.4.0 core: one bare
SDL window for Windows, macOS and Linux, driven by the command line and
`settings.ini`, shipped alongside the WinForms build (see `roadmap.md`).

Before any cross-platform work, the whole solution moves from .NET 8 to
.NET 10, so MZRakuCLI is built and tested on the runtime it ships on.
.NET 8 and .NET 9 reached end of support on 2026-11-10; .NET 10 is the
current LTS release, supported to November 2028. .NET 11 (STS, also
released 2026-11-10) has a similar end date but offers nothing MZRaku
needs, and LTS is the conventional choice.

### Ground rules

Carried over from v1.5.0:

- **Suite after every change.** `python tools/regress/regress.py`
  (windowed) and `--headless`, both all-pass, before every commit.
- **Goldens change only on purpose.** A changed golden is approved by
  the user in the same step, with the reason in the commit.
- **Persisted names stay.** `settings.ini` keys and sections, the
  comments Settings.Save writes, `.mzkbd` contents, HostKey names and
  MachineType values don't change.

## Phase 0 — Move to .NET 10

Agreed 2026-11-17. Shipped on its own as **v1.5.1** (no new features)
once done: v1.5.0's framework-dependent zip needs the .NET 8 runtime,
now out of support, and the rest of v1.6.0 is a long arc.

### Trial (2026-11-17, scratchpad copy, repo untouched)

- Only the .NET 10 SDK is installed (10.0.403); it has been building
  the `net8.0` targets all along.
- Core, MZRakuHeadless and Z80Core retargeted with no code changes;
  headless suite 45/45.
- The app gave 5 errors, all **WFO1000** (a new WinForms analyser rule:
  public properties on custom controls must say how the designer
  serializes them). All five are runtime-only properties on keyboard
  editor controls: `KeyboardMatrixGrid.ShowCoverage`,
  `KeyCaptureControl.Capturing` and `.SpecialKeyLabels`,
  `MzKeyboardDiagram.PcKeyLabels` and `.UnreachableKeyIds`.
  `[DesignerSerializationVisibility(Hidden)]` on each gave 0 warnings,
  0 errors.
- The windowed suite stopped at the **HostKey startup check** in every
  instance (the box waits for OK, so cases ran into their timeouts).
  Values still match `Keys`, but WinForms 10 swapped the declaration
  order of three alias pairs in `Keys`, so `Keys` formats them with the
  other name. `HostKey`, which is what saved names come from, formats
  them the same on both runtimes (corrected 2026-11-21; the first
  version of this table had 0xE2 the wrong way round):

  | Value | `HostKey`, .NET 8 and 10 | `Keys`, .NET 8 | `Keys`, .NET 10 |
  |---|---|---|---|
  | 0xC0 | `Oem3` | `Oem3` | `Oemtilde` |
  | 0xDE | `Oem7` | `Oem7` | `OemQuotes` |
  | 0xE2 | `OemBackslash` | `OemBackslash` | `Oem102` |

  The check also reported the combined-modifier strings built from
  those values (e.g. `Oemtilde, Shift`), 340+ in all. The headless
  runner never shows the box, which is why it passed.

### Steps

1. **Key names that don't depend on WinForms.** Survey (2026-11-21):
   names are written only by `KeyOverride.SerialiseLines`
   (`settings.ini` `[KeyOverrides.*]` and `.mzkbd`), which formats
   `HostKey`, never `Keys`; they are read by `Enum.TryParse<HostKey>`
   (overrides, `.mzkbd`, `--keys`), which already accepts every name of
   a value. The HID Diagnostic, Settings change summary and binding
   editor format `HostKey` too. Only the startup check and the capture
   banner's fallback used `Keys` formatting. Changes, on .NET 8:
   - `HostKeyParity` compares names and values as sets, not
     declaration order or `ToString()`.
   - New `Core/Host/HostKeyNames`: pins the saved name of all 16
     values with more than one name (.NET documents that `ToString()`
     may pick any of them) and fails if the runtime disagrees or a new
     shared value appears unpinned. Run by the app and the headless
     runner.
   - In `--dump` runs the startup checks warn on stderr instead of a
     dialog, so the windowed suite can't stop on one again.
   - The capture banner formats through `HostKey`.
   Saved `settings.ini` and `.mzkbd` files are unchanged.
2. **Retarget** `MZRaku.csproj` (`net10.0-windows`),
   `Core/MZRaku.Core.csproj`, `tools/MZRakuHeadless`,
   `tools/MzfBuilder` and `tools/RomAnalyse` (`net10.0`), with the
   WFO1000 attributes. `regress.py`'s `BUILD` and `HEADLESS_BUILD`
   paths follow. Build 0 warnings, 0 errors; the XML-doc check stays
   clean. **Done 2026-11-21:** all four buildable projects 0 / 0, doc
   check clean, Release single-file publish clean; headless and
   windowed suites 45/45 on .NET 10, no startup warnings.
3. **The user's bin folder.** Build output moves from
   `bin\Debug\net8.0-windows` to `bin\Debug\net10.0-windows`. The user
   copies their ROMs, games and settings across; Claude doesn't touch
   them. **Done 2026-11-21.**
4. **Verify.** Headless and windowed suites 45/45 (windowed only after
   step 1, so nothing stops at the check's box). Live: start-up on all
   three machines, a keyboard override using one of the three keys
   saved and reloaded, `.mzkbd` export / import. **Done 2026-11-21:**
   suites 45/45; user's start-up check on all three machines; a
   scripted load / save through Core on .NET 10 of overrides in both
   spellings (old names kept, WinForms 10 names saved as the pinned
   ones, second save byte-identical, rest of the file unchanged); live,
   a fixed-label key (CR) bound through the key editor, saved,
   exported, reset and imported. On a UK keyboard the `\|` key beside
   left Shift is `OemPipe` (0xDC, also pinned), not 0xE2, which is the
   extra key on layouts such as German.
5. **Docs and packaging.** README (runtime link and Desktop Runtime
   version, build instructions), `release-check.md`,
   `docs/developer/architecture.md`; the small zip becomes
   `MZRaku-<version>-dotnet10.zip`. Release notes say the small zip now
   needs the .NET 10 Desktop Runtime; the standalone zip needs nothing.
   **Done 2026-11-21:** README (intro, .NET 10 SDK to build, Desktop
   Runtime link, self-contained option) held back to land with the
   v1.5.1 release commit, since the README describes the latest
   release; `release-check.md` zip name and runtime;
   `docs/developer/architecture.md` project diagram, plus a note that
   Z80Core stays `net8.0`.
6. **v1.5.1.** Release check, version bump, history, tag, GitHub
   release with both zips.

**Z80Core** is a separate repo and stays on `net8.0` for now: a
`net8.0` library runs inside a .NET 10 app on the .NET 10 runtime. Its
own retarget (library and ZexHarness sample) is a later small Z80Core
release.

### Decision 1 — Test strategy (agreed 2026-11-22)

The starting point: all 45 suite cases need the Sharp ROMs, and most
need BASICs and games too, which live only in the private information
repository. There are no firmware-free tests and no CI today.

Three layers:

1. **Local: Windows and WSL** (where most testing happens).
   - Windows: both suites, as now.
   - Linux under WSL: the headless suite, and MZRakuCLI's suite with
     no window or sound (`SDL_VIDEO_DRIVER=dummy`,
     `SDL_AUDIO_DRIVER=dummy`, through its `--dump` mode) against the
     same goldens.
   - Hands-on Linux checks (window, keys, sound) through WSLg.
   - Needs `regress.py` made portable: Windows paths (`roms\...`) and
     the `MZRaku.exe` name are built in today.
2. **GitHub Actions on every push** (the only way the suite runs on
   macOS without a Mac).
   - Matrix: Windows, Ubuntu, macOS arm64, plus macOS x64 while GitHub
     still offers an Intel runner. Standard runners are free for
     public repos.
   - Each run: build, headless suite, MZRakuCLI's no-window suite.
   - ROMs, BASICs and test software are fetched from the private
     information repository with a read-only token held as a
     repository secret. They exist on the runner only for the run;
     this is not distribution (they are already on GitHub in the
     private backup).
   - Safeguards: nothing ROM-derived is uploaded as an artefact or
     printed to the (public) log, only a pass/fail list and a diff
     summary on failure; workflows triggered by pull requests from
     forks never receive the secret (GitHub's default).
3. **A real Mac for feel** — window, keyboard, sound, `.app`
   packaging and Gatekeeper, which no runner covers. Default:
   1.6.0-preview builds for testers in the LaunchBox thread; fallback:
   a cloud Mac rented for a day of focused checks. Settled before the
   first preview.

### Decision 2 — Keyboard rework scope (agreed 2026-11-22)

The roadmap's first phase, built on the map in
`docs/developer/keyboard.md` (its inconsistencies and WinForms-shaped
lists).

**Structure** (no golden changes):

1. **One input contract.** Front ends send key down, text, key up and
   focus lost. The core pairs text with the pending key down (SDL's
   `SDL_EVENT_TEXT_INPUT` follows its key down but doesn't name the key, so
   the pairing serves both). The WinForms Shift-flag lag workaround
   moves into the WinForms front end; the core trusts the modifier
   state it is given.
2. **`HostKey` stays the core's key identity** (persisted names
   depend on it). The SDL front end translates SDL scancodes into
   `HostKey` through a table; by default Cmd counts as Ctrl and Option
   as Alt. No new key type, no settings migration.
3. **One layering pipeline** in the shared keyboard base (override,
   special key, char map). Machine differences become data: SHIFT and
   CTRL cells, special keys with their own SHIFT, the letter-case rule.
   One staging rule, one frame order; override stores become
   per-machine objects instead of statics.
4. **One auto-typer, one entry point.** Pacing stays per machine
   (scan-watching on the MZ-700 and MZ-800, fixed times on the MZ-80A).
   A defined rule for the auto-typer and live keys sharing the matrix.
5. **One hotkey table in Core** (actions with default bindings, able
   to differ by platform), used by WinForms, SDL and the headless
   runner, so the runner's copy goes.
6. **One keyboard-mode query** (ALPHA / LOCK / GRAPH) on all three
   machines, in place of the two mechanisms; MZRakuCLI's on-screen
   messages can use it.

**Fixes** (low priority, not critical to the phase; each with a suite
case):

- **MZ CTRL + letter**, untypable on every machine today: looked up by
  key identity while Ctrl is held, unless the combination is an app
  hotkey.
- **MZ-80A CTRL's two paths** reduced to one (today a key up can clear
  CTRL while Esc is held).

**Firmware-free keyboard tests.** A small xUnit test project (the
framework APVSRaku uses) checking host
events against the emulated hardware: a host key with modifiers,
then a strobe written to the PPI's port A and port B read as the ROM
reads it. No ROMs, so it runs on every CI runner from the start. It
covers host key to hardware port; what the ROM does with the port
(the character typed, the mode) stays the goldens' job.

**Out of scope:** letter case stays per machine (the MZ-80A keeps its
swap setting); the MZ-800 typer at the IPL menu stays in the backlog;
scan detection for the MZ-80A typer (research, a stretch at most); the
Mac default bindings themselves, chosen with the hotkeys in decision 4.

### Decision 3 — SDL binding and packaging (agreed 2026-11-22)

Checked against the state of things in November 2026: SDL3 has been
stable since early 2025 (3.4.x now) and SDL2 is in maintenance;
Silk.NET 3.0, which is to bring SDL3, is unreleased, and Silk.NET 2.x
offers only SDL2. The roadmap's "SDL2 via Silk.NET" is superseded.

The sister project **APVSRaku** (SDL3 from the start, alongside this
repo) already uses the same binding and has CI passing on all three
platforms. The two projects keep their approaches in step.

1. **SDL3 through `ppy.SDL3-CS`**, the binding osu! uses, on the same
   version as APVSRaku (2026.1002.1 at the time of writing). Its
   NuGet package carries native SDL3 for Windows, macOS (arm64, x64)
   and Linux (x64, arm64). Fallbacks if it stops suiting: the
   community `SDL3-CS` package, or a thin binding of MZRaku's own
   (MZRakuCLI needs about 30 SDL functions).
2. **Self-contained, trimmed single files, built on each platform's
   own CI runner**, with SDL3 bundled. Native builds matter: Apple
   Silicon needs every binary signed (at least ad hoc, done when
   building on a Mac); Native AOT can't cross-compile between
   operating systems; and a zip made on Windows loses the executable
   bit, so Linux and macOS ship as `.tar.gz` made on their runners.
   **Native AOT is a trial** within the phase: if the core compiles
   cleanly with it, the program is a few MB; if not, the trimmed
   build (a few tens of MB) ships. The workflow starts from
   APVSRaku's (`.github/workflows/ci.yml` there).
3. **Platforms.** Required: Windows x64, Linux x64, macOS arm64.
   Extras if they build and pass on their runners: macOS x64 and Linux
   arm64.
4. **macOS: a plain folder for the first release**, run from
   Terminal like Linux, not an `.app` bundle. A downloaded `.app` not
   moved by Finder runs from a random read-only location (App
   Translocation), so it can't see or write a `settings.ini` beside
   it; a plain folder keeps the portable-settings rule. The cost: the
   README documents clearing the download flag
   (`xattr -dr com.apple.quarantine`) or System Settings' "Open
   Anyway". The `.app` bundle, signing and notarisation (Apple
   Developer account, about $99 a year) wait for demand or the v2.0
   GUI. APVSRaku plans an unsigned `.app` with `settings.ini` beside
   the executable, which meets the same problem; the two projects
   share one answer.
5. **`settings.ini` next to the program on every platform.** If that
   folder can't be written, MZRakuCLI says so on the console and runs
   without saving, as `--settings=` already does.
6. **`--sdl-test`**, as in APVSRaku: open a window, draw a test
   pattern, play a tone, read a gamepad, so a user can check their
   setup before blaming the emulator. Also the CI smoke test, under
   SDL's dummy drivers.

**Out of scope:** Homebrew, Flatpak, distribution packages and a
Windows installer.

### Decision 4 — MZRakuCLI's first-release scope (agreed 2026-11-22)

Measured against the WinForms build's 19 command-line flags and about
20 menu shortcuts.

**Command line.** Every existing flag, with the same meaning:
`--mz700` / `--mz80a` / `--mz800`, `--basic`, a cassette path,
`--insert=`, `--display=`, `--scanlines`, `--speed=N`, `--settings=`,
`--keys=`, `--dump=` / `--dumpframe=` (CI's golden runs need them) and
`--help`. New: `--sdl-test`, `--fullscreen`, `--scale=N`, `--version`,
and `--mzkbd=<file>` (a keyboard file for that run only, read-only like
`--settings=`).

**Hotkeys.** One modifier, **Mod**: Ctrl on Windows and Linux, Cmd on
macOS (which leaves Ctrl free for MZ CTRL + letter on a Mac). Mostly
as in WinForms:

| Action | Hotkey |
|---|---|
| Load cassette (native file picker) | Mod+O |
| Load BASIC | Mod+B |
| Load BASIC source | Mod+Shift+B |
| Insert cassette for the machine's own LOAD | Mod+I |
| Reset | Mod+R |
| Pause | Pause, or Mod+. (Macs have no Pause key) |
| Quit | Mod+Q (Esc is BREAK) |
| Machine switch | Mod+Shift+1 / 2 / 3 |
| Window scale | Mod+1–4 |
| Full screen | Alt+Enter; Cmd+Ctrl+F on macOS |
| Volume | Mod+Up / Down |
| Mute | Mod+U |
| Screenshot | Mod+P |
| Scanlines | Mod+L |
| Hotkey list on screen | Mod+/ |

The table lives in Core's hotkey table (decision 2, item 5) and is
confirmed on a real Mac before release.

**Loading files.** Drag and drop onto the window first; Mod+O opens
SDL3's native file picker. An OS file picker doesn't go against the
"no dialogs" spirit: there are still no MZRaku dialogs.

**Mac MZ-key defaults** (deferred from decision 2). GRAPH and ALPHA
stay on F11 and F12: on a Mac that needs fn, or "Use F1, F2, etc. keys
as standard function keys", which the README explains. INST should
already be Shift+Backspace, since INST is SHIFT+DEL on the MZ (to
check in the phase). Overrides cover the rest. Final table confirmed
on a real Mac.

**On-screen messages.** Drawn over the picture, not into the emulated
frame, so `--dump` captures and goldens are unaffected; in the
machine's own font ROM (the user's file, so no font licence). They
cover: the machine at start-up, reset, pause, a cassette loaded or why
it failed, volume, mute, speed, where a screenshot was saved, keyboard
mode changes (ALPHA / LOCK / GRAPH, from decision 2's mode query) and
the hotkey list.

**Errors.** Fatal problems (a missing ROM, a bad setting) go to stderr
with a non-zero exit code, plus an SDL message box as in APVSRaku, so
a launcher user sees them; no message box in `--dump` runs (Phase 0's
lesson). On Windows the program writes to the console when started
from one, without opening a console window when started from a
launcher.

**`settings.ini`.** The same file and format as the WinForms build, so
both can share a folder. MZRakuCLI ignores GUI-only keys but keeps
them when it saves (to check: whether `Settings.Save` already keeps
keys it doesn't know; if not, a plan item). The joystick uses SDL's
gamepad API with the existing joystick settings where they apply.

**Left for the GUI** (as `roadmap.md`): debugger, memory viewer, Font
Sheet, HID and sound diagnostics, keyboard matrix, settings and
keyboard-editor dialogs. A terminal debugger stays a possible later
addition.
