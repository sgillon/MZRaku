## Area summaries

**Hardware — MZ-700 side (20 findings).** The MZ-700-side Hardware
area is functionally complete and stable after v1.1.0. Its
architectural bones — the four-layer keyboard stack, the
CharMap/SpecialKeyMap/MatrixReference triad with startup
cross-validation, the PIT/PPI/Sound service-manual-anchored
reference tables — read well and earn their keep on legibility
grounds. Debt clusters in three areas: parallel shape with
MZ-80A siblings landed via copy-and-adapt in v1.1; dead
scaffolding accreted during hardware-diagnostic bug hunts; and
doc drift where XML comments still assert MZ-700 specificity on
classes now shared with MZ-80A. No category-(a) blockers.

**Hardware — MZ-80A side (10 findings after dedupe).** Less
accumulated debt than the MZ-700 siblings because it landed
later, but with two shapes of finding. First, deep structural
convergence with MZ-700: Mz80aKeyboard, Mz80aCharMap[Overrides],
Mz80aSpecialKeyMap, Mz80aCassette and Mz80aVideo are all
near-clones of MZ-700 siblings. Second, dormant scaffolding + doc
drift: Mz80aCassette.FixupBasicProgramPointers and
Mz80aCassette.ResetTrapState are declared but never called;
MZ80A.Reset() is missing the ResetTrapState / Keyboard.ReleaseAll
calls its MZ-700 sibling makes; Mz80aMatrixReference's header
comments still say "TBC / pending empirical check" even though
entry-level annotations mark the same cells "user-confirmed
2026-07-05".

**UI/Keyboard (10 findings).** Phase 5.5's parameterise-not-duplicate
bet mostly holds: one shared MzKeyboardDiagram, KeyboardMatrixGrid,
KeyBindingEditorForm, VkBindingEditorForm, MzKeyEditorForm,
AdvancedKeyboardForm, and KeyCaptureControl now serve both
machines via IKeyboardEditorContext / IPhysicalKeyboardLayout.
Two real abstraction leaks slipped through: MzKeyEditorForm reads
MZ-700 CharMap.Defaults directly, and KeyCaptureControl reads
MZ-700 SpecialKeyMap.Labels. A cluster of v1.1 carry-forward
items (MZ-80A diagram PC-key labels + red outline, .mzkbd MZ-80A
export) is now sitting close to the abstractions that would land
them. Nothing categorised (a).

**UI/Diagnostics + UI/Debugger (9 findings).** In relatively
healthy shape — the five surviving files (FontSheetForm,
HidDiagnosticForm, SoundDiagnosticForm, DebuggerForm,
MemoryViewerForm) all read as intentional and largely current.
The audit surfaces mostly small hygiene: two dead members, two
stale in-flight phase comments, two clean extract-candidates
where sibling forms carry independent copies of the same
scaffolding. One structural item worth fixing:
HidDiagnosticForm still holds a Keyboard?/Mz80aKeyboard? split
that IKeyboardMatrix should collapse. **Factual note**: the
brief lists `UI/Debugger/Z80TestRunner.cs`, but that file no
longer exists in this repo — it moved to Z80Core/samples/
ZexHarness/ when Z80Core spun out (commit de616db), and per the
hard rule Z80Core is out of scope.

**UI/Settings + UI root (5 findings).** The Settings surface came
through v1.1 Phase 5 with real weight added but not fully
consolidated. SettingsForm.cs is 1322 lines mixing six concerns.
The snapshot/diff pair is the single clearest debt item: it
captures MZ-700 char/key overrides but not the MZ-80A ones, so
edits made in the Phase 5.5b MZ-80A Advanced Keyboard editor
pass the confirm-changes dialog silently. The MZ-80A safety gate
is likewise absent by design.

**Top-level + project structure (15 findings after dedupes).**
MainForm.cs (1984 lines) is the elephant. The two machine facades
(MZ700.cs, MZ80A.cs) have visibly converged since MZ-80A landed —
Pause/Resume/StepInstruction/StepFrame are byte-identical,
RunFrame's VBLANK-split loop is nearly so, and AccumulatePit
differs only in the numerator constants. IMachine covers the
debugger surface but stops short of Cassette/Sound/Video/Keyboard,
forcing MainForm to keep the two-branch pattern for every non-CPU
touch. Two concrete bugs surfaced: Environment.Exit(0) in
SwitchMachine skips FormClosing geometry save, and --dump on
--mz80a NREs at frame 120 because DumpState is MZ-700-only.

**Cross-cutting code-review-lens (5 findings after dedupes).** One
code-as-doc contradiction in Video.cs (attribute FG/BG swapped in
the class-summary block), a hot-path efficiency leak from
always-on trace scaffolding (Pit.WriteLog grows unbounded on
every PIT write because _traceEnabled ships hardcoded true),
three duplicated helpers (LoadEmbeddedIcon, MakeRelativeToBase /
MakeStorable, home-rolled Clamp shadowing Math.Clamp). No
release-blocking (a) findings.

### F-001 — Extract MzfImage from Cassette as top-level type

**Category:** (b)
**Files:** `Hardware/Cassette.cs:57-66`, `Hardware/Mz80aCassette.cs:29-46`, `MainForm.cs:894`
**Effort:** small

**What's there today.** MzfImage is a public nested class inside the MZ-700 Cassette class (Cassette.cs:57-66). Mz80aCassette references it externally as `Cassette.MzfImage` (Mz80aCassette.cs:46, :58, :79), and MainForm's MZ-80A pointer-dump diagnostic uses the same qualified name.

**Why it warrants a change.** The .mzf format is Sharp-family shared (Mz80aCassette's own class comment says so) but the container type carries the MZ-700 Cassette class's name. Any MZ-80A code path handling cassette images acquires a cosmetic dependency on the MZ-700 Cassette class purely because MzfImage sits inside it, which reads as accidental coupling rather than a real dependency.

**Proposed change.** Move MzfImage to a new top-level class in Hardware/MzfImage.cs (or fold into the existing CassetteFile.cs since both are format-level). Both Cassette and Mz80aCassette then reference it directly. Cassette.Parse stays where it is or moves alongside — the parser is format-level too, not machine-level.

**Justification:**
- Pros vs cons: +1 file, minor. Zero runtime change. Trims MZ-80A's cross-class reference from `Cassette.MzfImage` to `MzfImage`.
- Legibility: Positive small — the type name now matches its scope. A reader picking up Mz80aCassette no longer has to explain why MZ-80A code references an MZ-700 class as a container.
- Maintainability: Positive for v1.4.0 MZ-800 arc — MZ-800 will need its own cassette class and equally shouldn't import from Cassette.

**Related:** F-021

### F-003 — Ppi8255 / Pit8253 XML doc drift — still say MZ-700-only

**Category:** (b)
**Files:** `Hardware/Ppi8255.cs:5-25`, `Hardware/Pit8253.cs:5-22`
**Effort:** trivial

**What's there today.** Ppi8255.cs's class summary opens with `/// Intel 8255 PPI emulation for MZ-700.` and describes MZ-700 bit assignments (PC0 = cassette motor, PC3 = speaker gate, etc.). Pit8253.cs's class summary opens with `/// Intel 8253 PIT emulation for MZ-700.` and describes MZ-700 counter wiring. Both classes are actually shared: MZ80A.cs:24-25 constructs `Ppi8255 Ppi = new()` and `Pit8253 Pit = new()`, and Mz80aIoBus.cs:46-47 declares fields of those types.

**Why it warrants a change.** Doc lies. A reader inspecting either class from the MZ-80A side has to reconcile the MZ-700-specific wiring commentary against Mz80aIoBus's very different bit assignments. The class comment should identify the class as generic-8255/8253 and defer machine-specific wiring to the two IoBus classes.

**Proposed change.** Rewrite both class summaries: describe the chip's generic register layout / mode set, note it is consumed by both `IoBus` (MZ-700) and `Mz80aIoBus` (MZ-80A), and refer readers to those files for per-machine wiring. Delete the MZ-700-specific bit-meaning tables from the class summary — that context lives in IoBus.cs already.

**Justification:**
- Pros vs cons: Doc-only. Zero LOC or runtime change.
- Legibility: Positive — aligns the doc with reality.
- Maintainability: Positive for v1.4.0: MZ-800 will also consume Ppi8255 (per the MZ800-feasibility doc). Fixing the class-level doc now makes the generic vs machine-specific split explicit before a third consumer arrives.

**Related:** F-002, F-004

### F-007 — Cassette.OnLoaded event never subscribed on either machine — wire to status or delete

**Category:** (b)
**Files:** `Hardware/Cassette.cs:86,137,285`, `Hardware/Mz80aCassette.cs:56,89`, `MainForm.cs:233`
**Effort:** trivial

**What's there today.** Cassette (MZ-700) exposes `public event Action<string>? OnLoaded;` and raises it twice (DirectInject line 137, tape trap line 285). Its sibling `OnSaved` (line 87) is subscribed by MainForm.cs:233 (`_machine!.Cassette.OnSaved += msg => _statusLabel.Text = msg;`). Mz80aCassette mirrors this: declares `OnLoaded` at :56, fires it from DirectInject at :89 with a useful "Injected: {img.Filename} load=$... exec=$... size=..." message. Grep finds no subscriber for `OnLoaded` on either Cassette class.

**Why it warrants a change.** Asymmetric — the SAVE path status-bar-reports, the LOAD path doesn't on either machine, even though the event is fired and both Cassette classes carry the API for it. Either both LOAD paths should status-bar-report the same way (cheap parity with SAVE) or the event surface should be removed from both machines.

**Proposed change.** Prefer wiring: extend MainForm's Cassette event hookup (near line 233) with `Cassette.OnLoaded += msg => _statusLabel.Text = msg;` for both MZ-700 and MZ-80A. Users see the load succeed the same way they see the save. If wiring is judged noise, delete the OnLoaded events from both Cassette classes and remove the four `OnLoaded?.Invoke(...)` fire sites. Consideration: check MainForm's usage during CLI autorun so the load message doesn't overwrite a preferred status.

**Justification:**
- Pros vs cons: Wire path: +2-3 lines in MainForm. Delete path: -6 LOC. Runtime change under wire path is one line of status-bar text after LOAD.
- Legibility: Positive small either way. Currently the reader has to grep to discover OnLoaded has no consumer.
- Maintainability: Neutral. MZ-80A already replicates the OnLoaded pattern, so a consistent decision here applies to both machines.

**Related:** F-008, F-025

### F-015 — Extract shared base for MZ-700 / MZ-80A keyboard matrix state

**Category:** (b)
**Files:** `Hardware/Keyboard.cs:23-120`, `Hardware/Mz80aKeyboard.cs:28-118`
**Effort:** medium

**What's there today.** Keyboard and Mz80aKeyboard independently reimplement the same matrix-management scaffolding: `byte[] _rows = new byte[10]` field, `Dictionary<Keys, ActiveHold> _holds` field, `List<StagedPress> _stagedKeyBits` field, `const int LiveShiftStageFrames = 2`, `ReadRow(int)`, `PeekMatrixRow(int)`, `SetMatrix(int, int, bool)`, `ReleaseAll()`, and the `_pcShift`/`_pendingDownVk` bookkeeping. Both implement `IKeyboardMatrix`.

**Why it warrants a change.** The two files sit at 522 (Keyboard.cs) and ~350 (Mz80aKeyboard.cs) lines with roughly the top 100 lines of each being verbatim copies. The real per-machine differences get lost in the copied plumbing.

**Proposed change.** Extract an abstract `KeyboardMatrixBase : IKeyboardMatrix` in a new file that owns `_rows`, `_holds`, `_stagedKeyBits`, `LiveShiftStageFrames`, `ReadRow`, `PeekMatrixRow`, `SetMatrix`, `ReleaseAll`, plus the `ActiveHold` / `StagedPress` records. **What's there today.** MainForm.cs:1400 declares `public bool _traceEnabled = true;` — a public field with an underscore prefix; grep confirms it is never assigned `false` anywhere. At Start(), because `_traceEnabled` is true, `_machine!.Pit.WriteLog` and `_machine!.Mem.BankSwitchLog` are set to fresh `StringBuilder` instances. `Pit.Write` and `MZ700Memory.HandleBankSwitch` both call `WriteLog?.AppendLine(...)` on every event. Neither builder is ever cleared or nulled during a session — the file dump path only reads them once at `_bootFrames == _dumpFrame`.

**Why it warrants a change.** During a BASIC MUSIC playback the `Pit.WriteLog` StringBuilder grows by ~50-100 bytes per PIT write, forever. `Mem.BankSwitchLog` grows every time BASIC banks the monitor ROM. This is real per-instruction cost on the hot CPU path and unbounded heap growth, all of it dead work because the dump file is never written in normal runs.

**Proposed change.** Wire `_traceEnabled` (and `_dumpFrame`) to the `--dump=` CLI flag: only initialise `WriteLog` / `BankSwitchLog` / `_traceLog` if `dumpPath != null`. Change the public underscore-prefixed fields on MainForm to proper properties (F-063). Program.cs already threads dumpPath into the ctor; add dumpFrame the same way instead of `form._dumpFrame = dumpFrame;`.

**Justification:**
- Pros vs cons: Removes per-PIT-write allocation and per-bank-switch allocation for the 99.9% of runs with no `--dump`.
- Legibility: Positive — the trace scaffolding stops looking like an always-on cost.
- Maintainability: Positive for any future hot-path performance work.

**Related:** F-063, F-057
